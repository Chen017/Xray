**低操作负担的验收方式**

本次采用 Mihomo 官方 API 加载临时运行副本，仅修改用户授权的 NewNB 节点。原订阅文件不改，AI 分组保持美国，结束恢复香港主节点。提供可复用的 `tests/mihomo_ab.py`：自动备份、加载、恢复配置与所有选择组；`tests/collect_linux_metrics.py` 经 SSH 采集服务器逐线程和整机指标。避免另一个客户端进程被现有 TUN 再次代理。

详细流程及官方依据见 [XHTTP 测试方案](xhttp-benchmark-plan.md)。窗口交错实验中，仅把客户端 H2 单流接收窗口从 4 MiB 改成 16 MiB，吞吐由 405/418 提升到 674/828 Mbps，XMUX 和伪装配置未改，证明窗口是本次线路的重要限制。更大窗口的满载短请求延迟也变高，未据最高分改默认；当前官方 Mihomo YAML 尚无此调节项，诊断构建不作为长期部署方案。

**本轮需要纠正的技术细节**

- Xray 26.3.27 的 stream-up 服务端已经允许 stream-one 请求，单栈客户端可以独立做此对照，无需先改服务端 mode。
- maxConcurrency=1 的原帖建议针对多线程测速；XMUX 不会把一个 TCP 下载拆分到多条连接或多个 CPU 核心。
- Komari 总 CPU 50% 不能直接定位单线程瓶颈；若真只有一个 logical CPU 且稳定占用 50%，也不能简单断言唯一 CPU 已被跑满。
- TLS1.3 与 h2/ALPN 是不同协商项，前者不是后者的逻辑保证；这不构成新增健康检查功能的理由。
